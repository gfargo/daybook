# Post-v0.4.0 audit — July 2026

Comprehensive bug audit and forward-scope review of the daybook monorepo, run against `main` at
`39c7ec3` (v0.4.0).

**How to read this:** every entry below is a candidate GitHub issue. Entries marked **VERIFIED** were
reproduced by executing the real code — the observed wrong output is quoted. Entries marked
**NEEDS SAMPLE** are strongly suspected but need a real exchange export to confirm which of two
behaviours is correct.

File these with:

```bash
node scripts/file-audit-issues.mjs --dry-run       # preview, files nothing
node scripts/file-audit-issues.mjs                 # file all of them
node scripts/file-audit-issues.mjs --only B1,B2,B3 # file a subset
```

The script uses your local `gh` auth (no token lives in the repo) and skips any issue whose exact
title already exists, so it is safe to re-run. Once everything is filed, GitHub is the source of
truth — this file can be deleted or moved to the wiki.

## Audit method

- `pnpm typecheck` — clean
- `pnpm lint` — clean
- `pnpm test` — **fails on a clean checkout** (see B27); passes only after `pnpm build`
- Tax engine: six suspected defects proven with a scratch vitest file driving `computeTax()` directly
- Adapters + classifier: rules and parsers executed out-of-tree against crafted CSV/`RawEvent` inputs
- Regulatory claims cross-checked against IRS guidance and practitioner sources (cited inline)

## Severity scale

| Severity | Meaning |
| --- | --- |
| **CRITICAL** | Produces a wrong number on a filed tax form, silently |
| **HIGH** | Wrong tax numbers, or data loss, in a realistic scenario |
| **MEDIUM** | Wrong in an edge case, or silent data loss with limited blast radius |
| **LOW** | Cosmetic, DX, or metric-only |

## Summary

The v0.4.0 release is in good structural shape — types are strict, money is `Decimal` throughout,
lint and typecheck are clean, and 674 tests pass. The problems are concentrated in three places:

1. **Unpriced data is treated as $0 rather than as an error.** This is the single most dangerous
   pattern in the codebase. Combined with CoinGecko's free-tier 365-day history limit, a user
   exporting any year older than ~12 months gets a Form 8949 full of fabricated 100% capital losses,
   and the command exits 0. (B2, B3, B20)
2. **The default lot-pooling mode is no longer legal.** `lotPool` defaults to `universal`, which the
   IRS disallowed for tax years beginning 2025. (B1)
3. **The newer adapters and the classifier rule chain were not adversarially tested.** Nine of the
   fourteen adapters have a sign, grouping, or silent-drop defect. Rule ordering in the classifier
   lets earlier rules consume events that later rules needed. (B6–B19, B28–B30)

Recommended sequencing: **B1, B2, B3** before any further feature work — they affect every user's
filed numbers. Then B27 (so the test suite is trustworthy), then F2/F3 (so this class of bug gets
caught mechanically), then the remaining adapter fixes.

# Part 1 — Bugs

## B1. [CRITICAL] Default `lotPool: universal` is disallowed for tax years 2025+

<!-- labels: bug, tax-correctness, compliance -->

`packages/cli/src/config.ts:70` defaults `tax.lotPool` to `'universal'`.

IRS Revenue Procedure 2024-28 ended universal (cross-wallet) basis accounting effective
**January 1, 2025**. From tax year 2025 onward, basis must be tracked per wallet/account. Sources:
[The Tax Adviser](https://thetaxadviser.com/news/2024/oct/universal-accounting-for-digital-assets-concludes-but-safe-harbor-available),
[RSM](https://rsmus.com/insights/tax-alerts/2024/end-universal-wallet-rev-proc-2024-28-safe-harbor-relief.html),
[AICPA FAQs](https://www.aicpa-cima.com/resources/article/digital-asset-safe-harbor-rev-proc-2024-28-faqs),
[Rev. Proc. 2024-28 (PDF)](https://www.irs.gov/pub/irs-drop/rp-24-28.pdf).
*Content rephrased for compliance with licensing restrictions.*

It is now July 2026. Any user who ran `daybook export 2025` with a default config computed their
return using a method the IRS no longer permits, with no warning.

**What's needed**

- Make `lotPool` year-aware: `per-account` is the default for years >= 2025, `universal` for <= 2024
- Emit a hard warning (or refuse) when `universal` is explicitly requested for a year >= 2025
- Document the change and the migration path in the README
- Per-account mode already exists (#10 / PR #37) — this is about the default and the guard rails,
  not new machinery

Related: F4 (safe-harbor allocation tooling).

## B2. [CRITICAL] Unpriced disposals silently become $0 proceeds — fabricating 100% capital losses

<!-- labels: bug, tax-correctness -->

**VERIFIED.** In `packages/tax/src/compute.ts`, the `trade` and `fee_disposal` arms do:

```ts
const rawProceeds = legUsd ? new Decimal(legUsd).abs() : new Decimal(0);
```

When a disposal leg cannot be priced, proceeds default to `0`, so `gainLoss = 0 - costBasis` — a
fabricated total loss. The entry ID is pushed to `unpricedEvents`, but **the disposal is still
emitted into the tax result and onto the tax form.**

Reproduction — 1 ETH bought for $3,000, later swapped with no price available on either leg:

```
unpricedEvents: [ 'sell-unpriced' ]
disposal emitted anyway: [{ proceeds: '0', basis: '3000', gainLoss: '-3000' }]
```

A $3,000 capital loss that did not happen, on a filed return.

**What's needed**

- Do not emit a disposal whose proceeds cannot be determined. Collect it as a blocking error.
- `export` must refuse to write filing-grade output (`8949`, `schedule-d`, `txf`) while any
  disposal in the year is unpriced, unless the user passes an explicit `--allow-unpriced`
- Exit non-zero in that case
- Distinguish "provider has no data for this asset/date" from "the price lookup failed"
  (network down, bad API key, rate-limited) — today both return `null` and are indistinguishable

This is the highest-impact bug in the audit. It is what makes B3 dangerous rather than merely
inconvenient.

## B3. [CRITICAL] CoinGecko free tier has only 365 days of history, and Pro keys don't work

<!-- labels: bug, pricing -->

`packages/tax/src/pricing/providers/coingecko.ts` hardcodes `BASE_URL = 'https://api.coingecko.com/api/v3'`
and sends the API key as `x-cg-demo-api-key`.

Two problems:

1. **The public/demo plan limits historical data to the past 365 days**
   ([CoinGecko support](https://support.coingecko.com/hc/en-us/articles/4538747001881-What-is-the-historical-data-availability-or-granularity-)).
   daybook is a multi-year tax tool. Every price request for a date older than ~12 months returns
   `null` on the free tier. Via B2, each of those becomes a fabricated capital loss.
2. **Pro/paid keys are not supported.** Paid plans use the `pro-api.coingecko.com` host and the
   `x-cg-pro-api-key` header ([docs](https://docs.coingecko.com/reference/coins-id-history)). A user
   who pays for a key to get 10 years of history gets silently downgraded to the 365-day-limited
   public endpoint.

*Content rephrased for compliance with licensing restrictions.*

**What's needed**

- Select base URL and auth header based on key type (demo vs pro); make it configurable
- Detect and clearly report "this date is outside your plan's historical window" as a distinct,
  actionable error rather than a generic miss
- Document the free-tier limitation prominently — it determines whether the tool works at all for
  historical years
- See F5 for the broader multi-provider fix

## B4. [HIGH] Disposals spanning short- and long-term lots collapse into a single term

<!-- labels: bug, tax-correctness -->

**VERIFIED.** `LotBook.dispose()` (`packages/tax/src/lot-book.ts`) tracks only the *earliest*
acquisition date across all consumed lots and returns one `term` for the whole disposal.
`compute.ts` then recomputes that single term from `disposal.acquiredAt`.

Reproduction — 1 ETH held 2 years + 1 ETH held 1 month, sold together:

```
disposals: [ { asset: 'ETH', amount: '2', term: 'long-term', basis: '4000', lots: 2 } ]
```

Expected: two Form 8949 rows — 1 ETH long-term (basis $1,000) and 1 ETH short-term (basis $3,000).
Actual: one long-term row. **$3,000 of short-term gain is reported at long-term rates.**

Form 8949 requires short-term (Part I) and long-term (Part II) dispositions to be reported
separately, per lot.

**What's needed**

- `dispose()` should return one `DisposalResult` per consumed lot (or per contiguous term group),
  not one aggregate
- `buildForm8949Data` then paginates them naturally into the correct parts
- Verify Schedule D and TXF totals still reconcile after the split

## B5. [HIGH] Trade fees are subtracted once per out-leg instead of once per trade

<!-- labels: bug, tax-correctness -->

**VERIFIED.** In `compute.ts`, `totalFeeUsd` is summed once for the entry, then
`rawProceeds.minus(totalFeeUsd)` is applied *inside* the `for (const leg of outLegs)` loop.

Reproduction — one trade disposing two assets with a single $30 fee:

```
proceeds per disposal: [ '170', '170' ]   ->  total net proceeds 340
expected: 370  (gross 400 minus one $30 fee)
```

The fee is deducted once per out-leg. Any multi-asset disposal (multi-leg DEX swap, dust
consolidation, NFT-for-token) understates proceeds by `fee × (legCount - 1)`.

**What's needed**

- Allocate the entry's total fee across out-legs pro-rata by USD value, or deduct it once
- Add a regression test with a 2-out-leg trade
- While here: wire up `tax.feeAllocation` (see B22)

## B6. [HIGH] `parseTimestamp` parses non-ISO dates in local time — events land in the wrong tax year

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `packages/sources/src/_shared/csv-helpers.ts:147-152` only appends `Z` when the string
matches `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}`. Everything else falls through to bare `new Date(str)`,
which the ECMAScript spec parses as **machine-local** time.

Observed, same input, three machines:

```
input "12/31/2023 20:00"        TZ=UTC       -> 2023-12-31T20:00:00.000Z
                                TZ=America/New_York -> 2024-01-01T01:00:00.000Z   <-- tax year 2024
                                TZ=Asia/Tokyo       -> 2023-12-31T11:00:00.000Z

input "2024/01/15 12:34:56"     TZ=UTC       -> 2024-01-15T12:34:56.000Z
                                TZ=Asia/Tokyo       -> 2024-01-15T03:34:56.000Z
```

A December 31 sale moves into the next tax year depending on the operator's timezone. Holding
periods shift too. `M/D/YYYY` is the Robinhood statement format; `YYYY/MM/DD` appears in several
localized exports. Affects robinhood, gemini, and generic-csv, which all accept free-form dates.

Two more defects in the same function:

- `"2024-01-15 12:34:56 UTC"` matches the regex, but `hasTimeZone` tests for a trailing `Z`, so
  `Z` is appended -> `"2024-01-15T12:34:56 UTCZ"` -> Invalid Date -> **row silently skipped**
- 10-digit Unix *seconds* are not handled (only 13-digit ms) -> Invalid Date -> **row skipped**

Both confirmed: `parseTimestamp('2024-01-15 12:34:56 UTC')` and `parseTimestamp('1705321896')` both
return `undefined`.

**What's needed**

- Parse all known formats explicitly and construct via `Date.UTC(...)`; never fall through to
  `new Date(string)`
- Support `M/D/YYYY`, `YYYY/MM/DD`, trailing `UTC`/`GMT`, and 10-digit epoch seconds
- Warn (don't silently skip) on an unparseable timestamp
- Add a test that runs the suite under a non-UTC `TZ` — this bug is invisible under `TZ=UTC`, which
  is why CI never caught it

## B7. [HIGH] Rule 08 reuses one payment event for every NFT in a transaction

<!-- labels: bug, classifier, tax-correctness -->

**VERIFIED.** `packages/classifier/src/rules/08-nft-classification.ts:190-219`. `fungibleOuts` is
computed once per txHash group; the per-NFT loop always takes `fungibleOuts[0]`:

```ts
const payment = fungibleOuts[0]!;   // same event on every iteration
rawIds.push(payment.id);
legs.push(...payment.legs);
```

Buying 2 NFTs in one transaction with a single 2.0 ETH ($6,000) payment produces two
`nft_acquisition` entries that each carry the full $6,000 payment leg — **$12,000 of basis from a
$6,000 purchase.** The mirror case at line ~229 (`fungibleIns[0]`) multiplies *proceeds* across every
NFT sold in one transaction.

**What's needed**

- Allocate a shared payment/proceeds across the NFTs in the transaction (pro-rata, or evenly when
  no better signal exists) instead of duplicating it
- Record the allocation basis in `reason` so it's auditable
- Test: 2 NFTs / 1 payment, and 2 NFTs sold / 1 proceeds event

## B8. [HIGH] Rule 08 NFT-for-NFT branch deletes the fungible payment event entirely

<!-- labels: bug, classifier -->

**VERIFIED.** `08-nft-classification.ts:181-186`:

```ts
for (const f of [...fungibleIns, ...fungibleOuts]) {
  consumedEventIds.add(f.id);
}
```

The events are marked consumed but no `LedgerEntry` is created for them. An NFT-for-NFT trade with a
3 ETH sweetener produced `consumed: [eth:out, eth:in, eth:pay]` while the emitted entries referenced
only `eth:out` and `eth:in`. The $9,000 ETH outflow appears in no ledger entry and vanishes from tax
computation.

This is the only path in the rule chain that drops an event outright — rule 07 otherwise catches
everything.

**What's needed**

- Emit a `trade` or `fee_disposal` entry for the fungible leg, or fold it into one of the NFT entries
- Add a runner-level invariant test: every consumed event ID must appear in some entry's
  `rawEventIds` (this would have caught it)

## B9. [HIGH] Rule 02 consumes all Coinbase sends, so rule 03 cross-source matching never fires

<!-- labels: bug, classifier -->

**VERIFIED.** `02-cb-self-transfer.ts:37-59` consumes every Coinbase `crypto_out` that has a
counterparty — including the `isSelf === false` branch. Rule 03 never sees them.

Compounding it: `ownAddresses` is built from `config.accounts[].identifier`
(`packages/cli/src/commands/classify.ts:69-70`), which for an exchange account is an email address,
never a deposit address. So `isSelf` is effectively always false for exchange->wallet sends.

Coinbase send + Kraken deposit 4 minutes later:

```
transfer_external_out  raw=[coinbase:s1]
transfer_external_in   raw=[kraken:d1]
perRuleCounts: { "02-cb-self-transfer": 1, "03-cross-source-match": 0 }
```

Neither type has tax impact in `compute.ts`, so under `lotPool: per-account` the lot never moves to
Kraken. A later sale on Kraken finds no basis -> cost basis 0 -> **the entire sale price is reported
as gain.** With B1 making per-account the correct default, this becomes a mainline bug.

**What's needed**

- Rule 02 should only consume events it can positively classify as self-transfers, and leave the rest
  for rule 03
- Let users register deposit addresses per exchange account so `isSelf` can actually be true
- Consider a warning when a `transfer_external_out` is followed by an unmatched
  `transfer_external_in` of the same asset

## B10. [HIGH] Rule 03 runs before rule 04 and steals DEX swap legs

<!-- labels: bug, classifier, tax-correctness -->

**VERIFIED.** `03-cross-source-match.ts` matches on any `crypto_out`, with no `txHash` or DEX-router
awareness, and runs before rule 04 (DEX swap collapse).

A 1 ETH -> 3,000 USDC Uniswap swap at 12:05 plus an unrelated 1.0 ETH Kraken deposit at 12:02:

```
transfer_self         raw=[eth:swapout, kraken:dep]
transfer_external_in  raw=[eth:swapin]
perRuleCounts: { "03-cross-source-match": 1, "04-dex-swap-collapse": 0 }
```

Rule 04 then sees a 1-event group and bails (`if (group.length < 2) continue`). The taxable ETH
disposal becomes a non-taxable self-transfer, the 3,000 USDC gets **no basis lot**, and nothing is
flagged `unclassified`.

**What's needed**

- Rule 03 should skip events whose `txHash` group contains a known DEX router, or move DEX collapse
  ahead of cross-source matching
- Rule 03 should prefer the *nearest* match in time rather than the first in array order (see B30)
- Test: on-chain swap plus a coincidental same-asset exchange deposit inside the match window

## B11. [HIGH] Rule 05 bridge matching compares no amounts at all, over a 24-hour window

<!-- labels: bug, classifier -->

**VERIFIED.** `05-bridge-detection.ts:66-79` matches on asset equality and `0 <= Δt <= 24h` only.
Rule 03's ±0.5% amount tolerance was not carried over.

A 0.1 ETH bridge-out matched an unrelated 25 ETH Coinbase deposit 23 hours later:

```
transfer_self raw=[eth:bridgeout, coinbase:in] legs=[ETH -0.1, ETH +25]
```

A 25 ETH acquisition is reclassified as a non-taxable transfer and loses its basis lot.

**What's needed**

- Apply an amount tolerance wide enough for bridge fees (a few percent) but not unbounded
- Prefer the nearest-in-time candidate
- Consider requiring the destination chain to be plausible for the bridge in question

## B12. [HIGH] Bitget: base and quote totals accumulate independently (the #36 bug, unfixed here)

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `packages/sources/src/bitget/csv.ts:237-238`:

```ts
if (base) baseTotal = baseTotal.plus(base.abs());
if (quote) quoteTotal = quoteTotal.plus(quote.abs());
```

Two unguarded statements. A fill row with `Filled Amount` but a blank `Total` grows `baseTotal` only.
This is exactly issue #36, which was fixed in `bybit/csv.ts` (it interpolates from `Filled Price`,
and warns + excludes the fill when it can't). **The Bitget copy never received the fix.**

Two fills of one sell order, second row missing `Total`:

```
observed: [{BTC,-2},{USDT,30000},{USDT,-2,fee}]   warnings: []
expected: 2 BTC disposed for $60,000
```

Proceeds understated 50%, silently. `Filled Price` is present in the row and unused, so the same
recovery Bybit uses is available.

**What's needed**

- Port the Bybit paired-accumulation guard to Bitget
- Grep the other grouped-trade adapters (mexc, gateio, okx) for the same shape and fix as a set
- Extract the guard into `_shared/` so the next adapter inherits it

## B13. [HIGH] Binance: commission rebates are sign-flipped into fee disposals

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `binance/csv.ts:367`:

```ts
return value.includes('fee') || value.includes('commission');
```

Binance ledger operations `Commission Rebate`, `Commission Fee Shared With You`, and
`Commission History` are **positive income**, but they match `includes('commission')`. Line 213 then
negates the positive change and flags it as a fee. `isFeeOperation` is also tested before
`isIncomeOperation`, so the income branch is unreachable for these rows.

```
input:    1,2024-01-15 12:00:00,Spot,Commission Rebate,USDT,5,
observed: { type: 'fee_only', legs: [{ USDT, -5, feeFlag: true }] }
expected: { type: 'income',   legs: [{ USDT, +5 }] }
```

$5 of income is dropped *and* a bogus $5 deductible disposal is invented — a 2x error on the amount.

**What's needed**

- Match rebate/shared-commission operations as income before the fee check
- Test both `Commission Rebate` (income) and `Commission Fee` (fee) so the precedence is pinned

## B14. [HIGH] Binance: ledger rows grouped by timestamp alone fuse unrelated trades

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `binance/csv.ts:~149-153` builds the group key from time + account + remark, and
`normalizeOperationFamily` collapses `Buy`, `Sell`, `Transaction Related`, and `Convert` all to the
string `trade`. Every trade leg in the same second and account lands in one group.

Two independent bot fills in the same second, no Remark:

```
observed: ONE event, type 'trade', legs [BTC +0.05, USDT -1500, ETH +1, USDC -2000]
```

Two distinct trades fused into one 4-leg event. Proceeds/basis allocation across a 2-in/2-out event
is arbitrary, and neither disposal can be matched to its real counter-asset. High-frequency and bot
traders hit this constantly.

**What's needed**

- Include the asset pair in the group key where derivable, or cap groups at one in-leg + one out-leg
  plus fees
- When a group has 2+ in-legs and 2+ out-legs, warn — it is not safely interpretable
- Test with two same-second trades of different pairs

## B15. [HIGH] generic-csv: a `Sell` row with an unsigned amount is booked as a receive

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `generic-csv/csv.ts:~331-345` returns `'received'` as the default direction. The
outbound label list covers `withdraw`/`send`/`sent`/`debit`/`transferout` but omits `sell`, `sold`,
`spend`, `payment`, `gift`, and `burn` — even though the adapter's own `SENT_AMOUNT_ALIASES` include
`'sell amount'`/`'sold amount'`, so sells are clearly expected.

```
input:    Date,Type,Amount,Currency / 2024-01-15 12:00:00,Sell,1.5,ETH
observed: { type: 'crypto_in', legs: [{ ETH, '1.5' }] }   warnings: []
```

A disposal of 1.5 ETH recorded as an acquisition: the gain disappears and phantom basis is created.
No warning. This is the adapter recommended for any exchange without a dedicated parser, so it has
the widest reach.

**What's needed**

- Add the missing outbound labels
- Default to *warn and skip* rather than silently assuming `received` for unrecognized labels with
  unsigned amounts
- Document the canonical template's expected sign convention

## B16. [HIGH] Gemini: `Amount` is not a fiat alias, so sells are emitted one-sided with zero proceeds

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `gemini/csv.ts:38` — `'amount'` appears in `QUANTITY_ALIASES` but not in
`FIAT_AMOUNT_ALIASES`, so a fiat total in an `Amount` column is never read; the parser reconstructs
it from `Price × Quantity`. When `Price` is blank the trade is emitted with only the base leg, and
the code merely warns instead of skipping.

```
input:    2024-02-03 11:00:00,Sell,BTCUSD,0.5,21000,gem-1
observed: { type: 'crypto_out', legs: [{ BTC, '-0.5' }] }   unparsedRowCount: 0
```

A $21,000 sale becomes a transfer-out with zero proceeds — the classifier will treat it as
non-taxable. The $21,000 is sitting unread in the `Amount` column.

**What's needed**

- Resolve the `Amount` column by row shape (fiat total vs base quantity) rather than a fixed alias
  precedence
- Skip and warn on a trade row that yields only one leg, instead of emitting it
- Note: Gemini exports XLSX, so the CSV shape depends on how the user converts — worth documenting

## B17. [HIGH] MEXC: partially filled orders pair partial base against the full order amount

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `mexc/csv.ts:~272-285`. The status gate accepts anything containing `filled`, which
includes `"Partially Filled"`, but `Order Amount` is the value of the **whole** order while
`Filled Quantity` is only the filled part. There is no scaling by fill ratio, and `Order Quantity`
is present in the row but never read.

```
input:    123,BTCUSDT,...,30000,30000,0.01,0.02,600,Partially Filled
observed: [{BTC,'0.01'},{USDT,'-600'}]
```

$600 of basis for 0.01 BTC instead of $300 — implied price $60,000 against the $30,000 in the row.
**Cost basis 2x correct.**

**What's needed**

- Scale the quote amount by `filledQty / orderQty`, or derive it from `Filled Price × Filled Quantity`
- Treat `Partially Filled` explicitly rather than via a substring match on `filled`
- Test a partial fill and a full fill

## B18. [HIGH] Any `side` value that isn't exactly `buy` is silently treated as a sell

<!-- labels: bug, adapter, tax-correctness -->

**VERIFIED.** `bitget/csv.ts:264`, same pattern at `bybit/csv.ts:~249` and `mexc/csv.ts:~180,~282`:

```ts
const isBuy = side === 'buy' || side === '买入';
```

Exact equality, no else-branch, no warning. The hardcoded `买入` proves localized exports are
expected, yet there is no handling for `"Buy Limit"`, `"BUY_LIMIT"`, traditional-Chinese `買入`, or an
empty cell.

```
Bitget, Side = "Buy Limit":  [{BTC,'-1'},{USDT,'30000'}]   <- a buy recorded as a disposal
Bybit,  Side = "" (blank):   { type: 'trade', legs: [{BTC,-1},{USDT,30000}, ...] }
```

Both silent. Bybit warns for a missing Symbol and a missing Time but never for a missing side. An
unrecognized side string inverts **every trade in the file**.

**What's needed**

- Normalize side robustly (substring/prefix match, both Chinese forms, common suffixed variants)
- Warn and skip on an unrecognized or empty side — never default to sell
- Extract into `_shared/` and reuse across the grouped-trade adapters

## B19. [HIGH] Gate.io: event IDs derive from row position, breaking idempotent re-sync

<!-- labels: bug, adapter -->

**VERIFIED.** `gateio/csv.ts:107` uses `` `__row__${syntheticGroupIndex++}` `` as the grouping key
when `action_data` is absent, and line 204 embeds that key in the event ID. The counter only advances
for rows lacking `action_data`, so an ID depends on how many such rows precede it in the file.

Same BTC deposit, two overlapping exports:

```
export A:  gateio:crypto_in:__row__0 -> BTC,  __row__1 -> ETH
export B:  gateio:crypto_in:__row__0 -> SOL,  __row__1 -> BTC,  __row__2 -> ETH
```

The BTC deposit is `__row__0` in one sync and `__row__1` in the next, so the upsert **inserts it
twice**; meanwhile `__row__0` now points at a different asset, silently mutating a previously stored
event. This violates the documented contract in `ledger/src/types.ts` that re-running an adapter
against the same source data must produce the same IDs.

**What's needed**

- Derive the fallback ID from row content (hash of timestamp + asset + amount + type), never position
- Add a cross-adapter test: parse a file, parse a superset of that file, assert the shared rows keep
  identical IDs

## B20. [HIGH] `export` writes tax forms and exits 0 even when disposals are unpriced

<!-- labels: bug, cli, tax-correctness -->

`packages/cli/src/commands/export.ts` prints `Unpriced events: N` and a hint, then writes the PDF/TXF
anyway and returns normally.

Combined with B2 and B3, a user running `daybook export 2022 --format 8949` on a free CoinGecko key
gets a Form 8949 PDF full of fabricated 100% losses, a zero exit code, and one informational line in
stdout.

Separately, several paths `return` after only a console message and no file write —
`--format 8949` with no disposals, `schedule-d` with no disposals, `--per-box` with no pages, and the
no-entries case. So `daybook export … --format 8949 && upload out.pdf` succeeds against a stale or
absent file.

**What's needed**

## B23. [MEDIUM] Leap years: an exactly-one-year holding is classified long-term

<!-- labels: bug, tax-correctness -->

## B30. [MEDIUM] Classifier pairing is positional, so unrelated history gets new entry IDs

## B33. [MEDIUM] Coinbase sync cursor advances past data it never ingested

## B34. [MEDIUM] Price cache is keyed too loosely, letting one trade's execution price become the day's price

<!-- labels: bug, pricing -->

`SourceReportedProvider` does not set `cacheMode`, so it defaults to cacheable. `PricingChain` then
writes its result into the shared cache under `(asset, day)`, and `PriceCache.get()` reads
`WHERE asset = ? AND day = ?` ordered by `fetched_at DESC` — ignoring `source` entirely, even though
the table's primary key includes it.

Consequences:

- A source-reported price is a **single transaction's execution price**, including that venue's
  spread and fee treatment. Caching it as *the* price for that asset that day means every other
  event for that asset on that day is valued using one unrelated trade's fill price.
- Because `get()` ignores `source` and orders by `fetched_at`, a later low-quality write shadows an
  earlier better one non-deterministically.

Two more pricing defects in the same area:

- **`fetchByContract` ignores the configured platform.** It loops over all of `PLATFORM_IDS` and
  returns the first hit, so a Polygon token address is tried against Ethereum first — and addresses
  can collide across chains. `this.platform` is dead config.
- **`PLATFORM_IDS` only has ethereum and polygon-pos**, but v0.4.0 added arbitrum, base, optimism,
  and bnb (PR #30). Contract-address pricing silently fails — or resolves against the wrong chain —
  for four of the six supported EVM chains.

**What's needed**

- Mark source-reported as `cacheMode: 'bypass'`, or cache it under a per-event key rather than
  per-day
- Make `PriceCache.get()` source-aware with an explicit provider preference order
- Add the four missing CoinGecko platform IDs and honour the configured platform
- Record which provider priced each leg so an export is auditable (see F6)

# Part 2 — Features and extensions

## F1. `daybook doctor` — integrity audit of the local ledger

<!-- labels: enhancement, cli, dx -->

The audit above found that daybook's failure mode is *silence*: unpriced legs become $0, dropped rows
increment nothing, missing basis produces a warning buried in a list. A dedicated audit command turns
these into something a user can act on before filing.

**Proposed checks**

- Disposals with no basis, or with basis covering less than the disposed amount
- Unpriced legs, grouped by asset and date, with a copy-pasteable `overrides set` command per group
- Negative running balances per (asset, account) — proof that imports are incomplete
- Assets held with no acquisition event at all
- Duplicate or colliding `RawEvent` IDs; stale classifier overrides; orphaned `rawEventIds`
- Coverage gaps: per account, first and last event date, and suspicious quiet periods
- Events classified `unclassified` or `nft_event`, counted by source
- Cross-check: sum of income + disposals per year against a naive recomputation

**Shape**

```
daybook doctor [--year 2025] [--format json] [--fix-suggestions]
```

Exit non-zero when any CRITICAL check fails, so it can gate a filing workflow. This is the highest
value single addition — it makes the tool self-auditing rather than silently wrong.

## F2. Golden-file fixture suite and an adapter conformance kit

<!-- labels: enhancement, testing, adapter -->

Nine of fourteen adapters have a sign, grouping, or silent-drop defect (B12–B19, B31, B32, B39–B42).
Every one of them is the kind of bug a golden-file test catches immediately. The current tests are
hand-written fixtures that encode the same assumptions as the parser they test.

**Proposed**

- `packages/sources/fixtures/<source>/<case>.csv` + committed `expected.json` of the full
  `RawEvent[]`, from **real redacted exports** rather than invented rows
- A shared conformance kit every adapter runs, asserting invariants independent of source:
  - every trade group balances — no base total without a quote total
  - every dropped row produces a warning and increments `unparsedRowCount`
  - IDs are stable across a re-parse, and stable when the file is a superset of a previous export
  - IDs are unique within a parse
  - fee legs always carry `feeFlag`
  - no leg amount is `NaN`, and no timestamp is invalid
  - parsing is invariant under `TZ` (would have caught B6)
- A documented redaction script so users can contribute samples safely
- Wire the `needs-sample` issues (B39, B40, B41, #35) to this — each is blocked on one real export

## F3. Property-based invariants for the tax engine

<!-- labels: enhancement, testing, tax-correctness -->

`fast-check` is already a dependency and used for Form 8949 pagination. Extend it to the engine
itself, where the money is.

**Proposed invariants**

- **Quantity conservation** — for every asset: acquired − disposed == remaining lot quantity
- **Basis conservation** — sum of `lotsConsumed[].costBasis` == `DisposalResult.costBasis`
- **No negative pools** — no lot's remaining amount ever goes below zero
- **Term partitioning** — every `lotsConsumed` entry's own holding period agrees with its row's term
  (this is exactly B4, and this invariant would have caught it)
- **Fee conservation** — total fees deducted across a trade's disposals == the trade's fee total
  (would have caught B5)
- **Method ordering** — for a pure-gain history, HIFO total gain <= FIFO total gain
- **Cross-format agreement** — CSV, 8949, Schedule D, and TXF totals all reconcile
- **Determinism** — same input, byte-identical output; and output invariant under input permutation
  (would have caught B30)

## F4. Rev. Proc. 2024-28 safe-harbor allocation and per-wallet migration

<!-- labels: enhancement, tax-correctness, compliance -->

Follows B1. Users transitioning from universal to per-wallet basis needed a reasonable allocation of
unused basis to each wallet as of January 1, 2025, and need to retain records of how they did it
([AICPA FAQs](https://www.aicpa-cima.com/resources/article/digital-asset-safe-harbor-rev-proc-2024-28-faqs),
[Rev. Proc. 2024-28](https://www.irs.gov/pub/irs-drop/rp-24-28.pdf)).
*Content rephrased for compliance with licensing restrictions.*

daybook is unusually well placed to do this well, because it already holds the full lot history.

**Proposed**

- `daybook allocate-basis --as-of 2025-01-01 [--strategy ...]` — snapshot universal lots and assign
  them to specific accounts
- Persist the allocation as a first-class, immutable record (new table + migration), since it's the
  documentation a taxpayer must retain
- Support the plausible strategies and let users compare outcomes before committing
- Emit a human-readable allocation report suitable for handing to a CPA
- Refuse to compute a 2025+ return per-account until an allocation exists (or the user asserts a
  clean per-wallet history)

## F5. Multi-provider pricing with explicit provenance

<!-- labels: enhancement, pricing -->

B3 shows a single free-tier provider cannot price a multi-year history. Pricing needs to be a
pluggable, auditable layer rather than one hardcoded vendor.

**Proposed**

- Additional providers behind the existing `PricingProvider` interface — candidates: CryptoCompare,
  CoinMarketCap, Kaiko, Amberdata, and on-chain TWAP/pool-derived pricing for long-tail tokens
- Provider chain configurable in `config.tax`/`config.pricing`, with per-provider credentials
- Replace the hardcoded ~30-entry `TICKER_TO_COINGECKO_ID` map with a cached `/coins/list` lookup
  plus contract-address resolution — the current list is explicitly "the assets present in the
  user's real data" and doesn't generalize to anyone else
- Clear, actionable errors distinguishing no-coverage, outside-plan-window, rate-limited, and
  auth-failed
- Record the resolving provider and the raw response per priced leg

## F6. Reproducible, auditable exports — price lockfile plus manifest

<!-- labels: enhancement, tax-correctness, dx -->

A filed return must be defensible years later, potentially after the price APIs have changed their
history or gone away. Today, re-running `daybook export 2024` can produce different numbers with no
record of why.

**Proposed**

- `daybook prices lock <year>` writes a committed price set: asset, date, price, provider, fetch
  timestamp
- `export --prices-lock <file>` computes purely from the lockfile, hitting no network
- Every export emits a sidecar manifest: daybook version, config hash, cost-basis method, lot-pool
  mode, input event count and content hash, price-set hash, per-leg price provenance
- `daybook verify <manifest>` re-runs and asserts byte-identical output
- Makes `compare` trustworthy too, since all methods then price identically

## F7. Capital loss carryforward across years

<!-- labels: enhancement, tax-correctness -->

`computeTax` treats each year independently. Net capital losses are limited annually (currently
$3,000 for most individual filers) with the remainder carried forward indefinitely — so a
single-year view can materially misstate the tax outcome for anyone with a loss year.

**Proposed**

- Persist per-year net short-term and long-term results
- Apply the annual limitation and track the carryforward balance by character
- Surface carryforward on Schedule D and in the export summary
- `daybook summary --all-years` showing the multi-year picture
- Prerequisite for the multi-year view in F8

## F8. Income reporting beyond a summary total

<!-- labels: enhancement, tax-correctness -->

`IncomeSummary` gives a total and a per-asset breakdown, but income never reaches a form. Staking
rewards, airdrops, and interest are ordinary income and belong on a return.

**Proposed**

- Classify income by character (staking, mining, interest, airdrop, referral, hard fork, payment for
  services) — the classifier already distinguishes several of these
- Route to the right destination and generate the corresponding output
- Per-event detail export with date, asset, quantity, FMV, and price provenance
- Reconcile against exchange 1099-MISC/1099-INT where available
- Also fixes the gap in B24 (USD-denominated income)

## F9. Balance reconciliation against exchange-reported balances

<!-- labels: enhancement, cli, tax-correctness -->

`daybook reconcile` compares disposals against a 1099-DA. That catches disagreements about events
daybook *has*. It cannot catch events daybook is **missing** — which, given B32, is the more likely
failure.

Comparing computed holdings against actual current balances is the cheapest possible check on import
completeness: if daybook thinks you hold 1.2 ETH and Coinbase says 3.7, something wasn't imported.

**Proposed**

- `daybook reconcile-balances [--source coinbase]` comparing computed vs reported holdings per
  (account, asset)
- Pull live balances where an API exists (Coinbase today); accept a simple CSV/JSON otherwise
- Report deltas ranked by USD impact, with likely causes (missing import, unmatched transfer,
  dropped rows)
- Wire into `daybook doctor` (F1) as a check

## F10. Wash-sale disallowance computation, opt-in

<!-- labels: enhancement, tax-correctness -->

Wash-sale flagging is informational: `washSaleFlag` is set, no disallowance is computed. That is a
defensible default, since §1091 addresses stocks and securities and digital assets are generally
treated as property — but users holding tokenized securities, or wanting to model a rule change, have
no path, and the current flag is over-broad (any acquisition in the window, regardless of quantity).

**Proposed**

- Opt-in `--wash-sale-mode=disallow` that computes the disallowed loss, adjusts replacement-lot
  basis, and extends the holding period
- Match replacement quantity properly rather than flagging on mere existence
- Per-asset configuration so it can be enabled only where it applies
- Document clearly that this is off by default and why

## F11. Kraken and Binance API sync

<!-- labels: enhancement, adapter -->

Coinbase has API sync (#12, PR #34). Every other exchange is manual CSV export, which is the step
users forget — and stale imports are exactly what F9 exists to detect.

**Proposed**

- Kraken REST (`TradesHistory`, `Ledgers`) and Binance (`myTrades`, and the ledger/income endpoints)
- Reuse the `sync_state` incremental machinery — but fix B33 first, since these will inherit it
- Ensure API-sourced and CSV-sourced events produce identical `RawEvent` IDs so users can switch
  without duplicates (this was an explicit acceptance criterion on #12 and is worth a shared test)
- Encrypted credential storage rather than plaintext env vars (F12)

## F12. Encrypted credential storage

<!-- labels: enhancement, security -->

API credentials come from environment variables (`COINBASE_CDP_PRIVATE_KEY`, Alchemy keys, CoinGecko
keys). For a self-hosted tool handling complete financial history, that means secrets in shell
history, in `.env` files at risk of being committed, and readable by any process.

**Proposed**

- OS keychain integration (macOS Keychain, libsecret, Windows Credential Manager) with an encrypted
  file fallback
- `daybook auth set/list/remove <source>`
- Keep env vars supported for CI, but warn when used interactively
- Redact secrets from all error output and logs — worth an audit pass of its own
- Document the local threat model, including that `~/.daybook/data.db` is unencrypted

## F13. Adapter plugin API

<!-- labels: enhancement, architecture -->

Every new exchange currently requires a PR to the monorepo, a new `SourceId` union member, and edits
to CLI validation and sync routing. That is a hard ceiling on coverage, and the adapter surface is
where most bugs live.

**Proposed**

- Publish the adapter contract (`RawEvent`, leg sign convention, ID stability rules) as a stable API
- Load third-party adapters from config by package name; make `SourceId` extensible
- Ship the F2 conformance kit as a package so third-party adapters can prove correctness
- Document ID-stability and warning requirements as hard obligations, not conventions

## F14. `daybook prices` — inspect, pin, and export the price set

<!-- labels: enhancement, cli, pricing -->

Pricing is the least observable part of the pipeline and, per B2/B3/B34, one of the most error-prone.
`overrides set` is the only interaction, and it's write-only and blind.

**Proposed**

- `daybook prices list --year 2024 [--asset ETH]` — every price used, with provider and fetch time

- `daybook prices refresh --asset X --date Y` — invalidate and refetch

## F15. Docs: adapter coverage matrix, pricing trust page, per-wallet basis change

<!-- labels: documentation -->

For a self-hosted tax tool, "how much should I trust this number" is the central user question, and

**Proposed**

- **Adapter coverage matrix** — per source: which export format, what's covered (trades, deposits,

## F16. Performance: streaming parse, batched inserts, and a benchmark suite

<!-- labels: enhancement, performance -->

Several paths are structurally quadratic or fully materializing: `hydratePrices` (B35), wash-sale
matching (B36), `repo.getLedgerEntries({ limit: 1_000_000 })` loading all history into memory in
`export`/`compare`/`reconcile`, and CSV parsers building complete row arrays before emitting.

None of this matters at 1k events and all of it matters at 500k. There's currently no benchmark, so
regressions are invisible.

**Proposed**

- Stream CSV parsing; batch `insertRawEvents` in transactions
- Paginate or stream ledger reads in the tax engine
- Fix the quadratic loops (B35, B36)
- A committed benchmark with a synthetic 100k-event fixture, tracked in CI
- Document expected resource use at 10k / 100k / 1M events
